# AI Sana Challenge Hub

MVP для хакатона: бизнес превращает неполное описание в проверенную карточку задачи, студенческие команды предлагают решения, бизнес принимает или отклоняет предложения вручную.

## Архитектура

```text
React / Vite / TypeScript / Tailwind / React Router
                       ↓ HTTP / JSON
FastAPI api → business_logic → data_access → PostgreSQL
                    ↓
            OpenAI Python SDK
                    ↓
        Structured Outputs → Pydantic → проверка источников
```

`backend/app/api` — маршруты и контракты; `business_logic` — AI, переходы статусов и рейтинг; `data_access` — SQLAlchemy async и репозиторий; `core` — настройки. Две таблицы: BusinessTask и TeamProposal, UUID, FK с каскадным удалением, timestamps и CHECK constraints. Alembic управляет схемой. Отдельной модели Team нет: имя команды хранится в предложении.

## Запуск

Нужны Python 3.11+, Node.js 22+ и PostgreSQL (либо Docker). Команды выполняются из корня проекта, если не указано иначе.

1. Создайте `.env` по `.env.example`, если его ещё нет. **Не перезаписывайте существующий `.env`.** Ключ хранится только там. Переменные:

```dotenv
OPENAI_API_KEY=ваш_ключ
OPENAI_MODEL=gpt-4.1-mini
DATABASE_URL=postgresql+asyncpg://sana:sana@localhost:5432/sana
FRONTEND_ORIGIN=http://localhost:5173
```

2. Запустите PostgreSQL:

```sh
docker compose up -d db
```

Либо создайте пользователя `sana`, базу `sana` на своём PostgreSQL и укажите соответствующий `DATABASE_URL`. Пароль `sana` в compose предназначен только для локальной демонстрации, порт привязан к localhost.

3. Установите backend:

```sh
python -m venv .venv
# Windows PowerShell:
.venv\Scripts\Activate.ps1
# macOS / Linux: source .venv/bin/activate
python -m pip install -r backend/requirements.txt
cd backend
python -m alembic upgrade head
python -m app.seed
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Seed идемпотентный: 5 опубликованных задач разной заполненности (30, 65, 80, 100, 85 баллов) и 5 предложений. Это вымышленные демонстрационные данные. Повторный запуск не перезаписывает карточки и решения пользователя.

4. Во втором терминале:

```sh
cd frontend
npm install
npm run dev
```

Откройте http://localhost:5173. Swagger: http://127.0.0.1:8000/docs. Vite проксирует `/api` на backend; ключи и `.env` не входят в frontend. Production-сборка: `npm run build`; для deployment нужен reverse proxy `/api` на backend.

Для воспроизводимой установки проверенных версий используйте `backend/requirements.lock.txt` вместо `requirements.txt`, а во frontend — `npm ci` (есть `package-lock.json`).

## Локальные переносимые инструменты Windows

Если инструменты были скачаны в `.tools` при разработке, `scripts/start-local.ps1` запускает изолированный PostgreSQL на порту 55432, миграцию, seed, backend и Vite без установки системных служб. Папки `.tools` и `.pgdata` исключены из Git. Скрипт не требует менять ключ в `.env`. Зависимости должны быть предварительно установлены.

Повторный запуск проверяет реальные процессы и восстанавливает только остановленные сервисы. Старый PID-файл не мешает восстановлению; чужой процесс на занятом порту не останавливается. Успех выводится после ответа frontend и `/api/health`, который проверяет PostgreSQL и таблицы. Чтобы подхватить изменения Python-кода, выполните остановку и запуск.

```powershell
powershell -ExecutionPolicy Bypass -File scripts/start-local.ps1
# Остановка только процессов этого запуска:
powershell -ExecutionPolicy Bypass -File scripts/stop-local.ps1
```

## AI flow и источники

`POST /api/tasks/analyze` принимает `description`. OpenAI `responses.parse` возвращает Pydantic TaskAnalysis: известные идентификаторы missing_fields и минимум 3 разных непустых вопроса. Повторы с отличиями только в регистре, пробелах и пунктуации не считаются разными вопросами. После ответов frontend вызывает `POST /api/tasks/generate-with-sources` и получает `{card, sources}`. Совместимый `POST /api/tasks/generate` возвращает только Card.

Генерация намеренно экстрактивная: для каждого поля AI возвращает значение и дословную цитату из первоначального описания или ответа пользователя. Backend принимает значение только если оно равно цитате и действительно присутствует в источнике. Тексты вопросов не считаются фактами. Неизвестные сведения остаются null. Это ограничивает перефразирование, зато исключает появление новых неподтверждённых чисел, контактов и сроков. Смысловую корректность распределения по полям всё равно проверяет человек.

AI не рассчитывает рейтинг, не публикует карточки и не выбирает команды. Ошибка API, отказ или невалидный ответ обрабатываются; предусмотрена одна повторная попытка. После двух неудач интерфейс предлагает понятную ошибку и возможность заполнить карточку вручную. Нет скрытой подмены AI демоданными. Запросы используют `store=False`.

Интеграция: [официальная документация Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

## Рейтинг

Обычная функция `calculate_rating` в Python, никаких вызовов LLM:

| Сведения | Баллы |
|---|---:|
| Контекст | 10 |
| Потребность | 10 |
| Данные и материалы | 20 |
| Ожидаемый результат | 15 |
| Критерии успеха | 15 |
| Ограничения | 10 |
| Пользователи | 10 |
| Контакт **и** формат взаимодействия вместе | 10 |

Непустое поле после strip получает баллы. 0–39: draft; 40–69: working; 70–89: ready; 90–100: priority. Рейтинг измеряет полноту, а не достоверность или качество решения. Заголовок и отрасль баллов не дают. API возвращает score, level, missing и improvements. Форма получает предварительный рейтинг из `/api/tasks/preview`, после сохранения рейтинг записывается в БД.

## Публикация, каталог и предложения

Переходы: `draft → confirmed → published`. Для подтверждения достаточно названия; неполные карточки разрешены. Любое сохранение изменений возвращает задачу в draft, требует повторного подтверждения и публикации; связанные предложения сохраняются.

В каталоге только published. По умолчанию сортировка по убыванию рейтинга, затем дате и UUID. Есть сортировка по новизне, фильтры по точной отрасли и уровню. Низкий рейтинг не скрывает опубликованную задачу.

Команда отправляет имя, идею, план, оценку сроков и необязательную HTTP(S)-ссылку на прототип. Число предложений не ограничено. Начальный статус pending, бизнес вручную меняет его на accepted или rejected. Можно принять несколько команд и пересмотреть решение.

Это локальный демо-режим без авторизации: общий кабинет бизнеса доступен всем. Не размещайте его как публичный сервис с реальными контактами без добавления контроля доступа.

## Проверки

```sh
cd backend
python -m pytest -q
python -m alembic check
cd ../frontend
npm run build
npx playwright install chromium
npm run test:e2e
```

Из корня также запустите `python scripts/check_secrets.py`. Проверка сканирует публикуемые исходники и собранный frontend, не печатая найденные значения. Настоящий ключ размещайте только в `.env` или переменной окружения; `OPENAI_API_KEY` в `.env.example` должен оставаться пустым. Тесты проверяют и это условие, и правила исключения `.env` из Git.

Backend integration test использует настроенный PostgreSQL, создаёт свою задачу и удаляет её в finally. AI в автоматических тестах подменён, чтобы не тратить API-кредиты; отдельный реальный smoke test `python scripts/live_ai_smoke.py` из корня проверяет OpenAI через ваш ключ и делает два платных запроса. Он печатает только поля карточки, не ключ.

Browser test требует работающие backend и frontend. Полный UI flow подменяет только два AI endpoint; остальное проходит через реальный backend и PostgreSQL. Второй тест проверяет отображение ошибки AI.

`tests/workbench.spec.ts` проверяет разбор качества, ручное применение уточнений, помощника команды, сохранение и подтверждение пилота, повторное открытие и печать в PDF. В нём подменены только AI-ответы; база и остальные endpoint настоящие. `python scripts/live_workbench_smoke.py` отдельно вызывает три новые AI-функции на зашитом вымышленном примере пекарни (три платных запроса, без чтения карточек из БД).

Если Chrome уже установлен, вместо скачивания Chromium можно указать `$env:PLAYWRIGHT_CHANNEL = 'chrome'` в PowerShell. Третий тест `tests/live.spec.ts` по умолчанию пропускается. Для полного прогона с реальным OpenAI (два платных запроса): `$env:LIVE_AI = '1'; npx playwright test tests/live.spec.ts`. Он также проверяет мобильную ширину и сохраняет скриншоты в `.tools`. Браузерные тесты оставляют созданные демонстрационные карточки и предложения в кабинете.

Для backend-тестов на переносимой локальной базе перед запуском установите `$env:DATABASE_URL = 'postgresql+asyncpg://sana@127.0.0.1:55432/sana'`. Скрипт запуска задаёт эту переменную только своим дочерним процессам, не меняя `.env`.

## Demo / How to test

В шапке есть переключатель **«Я бизнес / Я команда»**. Выбранный режим сохраняется в браузере. В режиме бизнеса доступны создание и редактирование задач, кабинет и решения по предложениям; в режиме команды — каталог и отправка предложения. Это переключатель интерфейса для демонстрации, не система авторизации: API по-прежнему общий.

После AI-генерации под заполненными полями редактора можно раскрыть **источник**: точную цитату, первоначальное описание либо номер вопроса и его текст. Backend сам находит источник среди ответов; модель не назначает номер вопроса. Если изменить значение поля, источник помечается как исходная цитата до ручной правки. Источники показываются на этапе проверки свежесгенерированной карточки; в БД сохраняются подтверждённые поля, без истории цитат.

На странице предложений по умолчанию открывается **таблица сравнения**: команда, идея, план, сроки, прототип и решение. Можно переключиться на карточки. Принятие и отклонение работают в обоих видах; принятых команд может быть несколько.

1. Каталог: сравните рейтинг 5 демозадач, фильтры и сортировку.
2. Создать задачу: «Хотим с помощью ИИ уменьшить очереди в нашей клинике.» → «Уточнить с AI».
3. Ответьте на вопросы своими фактами. Часть ответов можно оставить пустыми.
4. Сформируйте карточку, проверьте поля, исправьте название и подтвердите сведения. Обратите внимание на исходный рейтинг.
5. Для учебной демонстрации вручную добавьте вымышленные сведения: пользователи — «Администраторы и пациенты»; данные — «Обезличенный журнал приёмов»; результат — «Прототип расписания»; критерии — «Снизить среднее ожидание на 20%»; ограничения — «Без персональных данных»; контакт — `clinic-demo@example.com`; формат — «Еженедельный созвон». Заполните контекст и потребность, если они остались пустыми. Рейтинг станет 100. Подтвердите обновлённые сведения → «Опубликовать».
6. Переключитесь на «Я команда». В каталоге найдите задачу на позиции согласно рейтингу. Проверьте фильтры отрасли и готовности, затем откройте детали.
7. Отправьте предложение от команды, например «Qadam», с идеей и планом.
8. Переключитесь на «Я бизнес», откройте «Предложения команд», сравните варианты → «Принять». Перезагрузите страницу: статус должен остаться «Принято». Проверьте «Отклонить» и перезагрузку; затем при желании примите предложение снова. Решения сохраняются в PostgreSQL.
9. У принятого предложения откройте **«Подготовить пилот»**. Проверьте цель и критерии из карточки, сроки из предложения. По желанию запросите этапы у AI, просмотрите их и нажмите «Перенести этапы в план».
10. Заполните обязанности бизнеса и команды, отредактируйте этапы → «Сохранить план» → «Подтвердить план пилота». Кнопка **«Печать / PDF»** открывает системную печать: выберите «Сохранить как PDF». Такая же кнопка есть в деталях задачи.

## Уточнение качества и подготовка пилота

**Разбор качества.** В редакторе карточки нажмите «Разобрать качество с AI». Модель задаёт вопросы по неясным формулировкам, недостающим сведениям и возможным противоречиям. Для заполненных полей backend проверяет дословные цитаты; для противоречия нужны цитаты из обоих полей. Неподтверждённые источником замечания отбрасываются. Поле контакта не отправляется на этот анализ. Это помощь в проверке, а не объективная оценка качества. Рейтинг по-прежнему вычисляет Python.

Впишите уточнённое значение поля и нажмите «Перенести ответы в карточку»: введённое значение **заменит** соответствующее поле, но не сохранится и не опубликуется автоматически. После изменения карточки старый анализ помечается неактуальным. Нажмите «Проверить ещё раз» для следующего раунда. Индикатор над формой сравнивает рейтинг при открытии редактора и текущий рейтинг; это не постоянная история всех изменений.

**Помощник команды.** В форме предложения сначала введите свою идею, затем нажмите «Улучшить предложение с AI». Модель предлагает подход, план и вопросы бизнесу. Это рекомендации, а не сведения о возможностях команды. Идея и план редактируются, затем переносятся в форму по отдельной кнопке. Сроки, имя команды и ссылка остаются введёнными командой; ничего не отправляется автоматически.

**Пилот.** Документ доступен для каждого принятого предложения отдельно. Факты (цель, результат, критерии, данные, ограничения и сроки) копируются из карточки и предложения обычной Python-логикой. AI предлагает только этапы и открытые вопросы. Обязанности сторон задаёт пользователь. Можно полностью подготовить пилот вручную без OpenAI.

План сохраняется в PostgreSQL (`TeamProposal.pilot_document`, JSON; миграция `0002`), отдельно хранится подтверждение бизнеса и отпечаток исходных данных. Изменённые исходные данные делают подтверждение неактуальным. Перед новым подтверждением необходимо проверить и сохранить актуальный план. Сохранение любых правок снимает подтверждение; отклонённой команде нельзя сохранять или подтверждать пилот. Подтверждение бизнесом не выдаётся за согласие команды.

Новые API: `POST /api/tasks/review`, `POST /api/tasks/{id}/proposal-coach`, `GET/PUT /api/business/proposals/{id}/pilot`, `POST .../pilot/generate`, `POST .../pilot/confirm`. AI-функции используют прежние Structured Outputs / Pydantic и обработку ошибок. Новых зависимостей нет.

При недоступности OpenAI проверьте ключ, доступ к выбранной модели и лимиты; сообщение в UI сохраняет введённый текст. При ошибке БД проверьте PostgreSQL, DATABASE_URL и миграцию. HTTP 404/422/409 обрабатываются в интерфейсе.
